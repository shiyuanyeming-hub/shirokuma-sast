# 汚染解析アルゴリズムの詳細

このドキュメントは `src/analysis/` の実装を、アルゴリズムの観点から説明します。
「なぜこの設計なのか」「どこで妥協しているか」を明示することを目的としています。

対象読者: 静的解析を実装したことがある、または実装しようとしている人。

---

## 1. 問題設定

やりたいことは 1 行で書けます。

> ソース集合 *S* の値が、伝播規則 *P* に従って、シンク集合 *K* に到達するか。

これを決定的に、有限時間で、説明可能な形で解くのが目標です。

### なぜ「到達可能性」だけでは不十分か

単純な到達可能性（グラフ探索）では、次の 2 つを区別できません。

```ts
// A: 危険
db.query('SELECT ... ' + req.query.id);

// B: 安全
db.query('SELECT ... $1', [req.query.id]);
```

B では汚染はシンクのノードに「到達」していますが、無害化されています。
したがって解析は「到達したか」ではなく
**「無害化されていない汚染が到達したか」** を判定する必要があります。

そこでトークンに **タグ集合** を持たせ、サニタイザでタグを落とす設計にしています。

---

## 2. 状態の定義

解析の状態は 4 つ組です。

```text
state = (node, source, tags, argIndex)
```

| 要素 | 意味 |
| --- | --- |
| `node` | 現在いる DFG ノード |
| `source` | どのソースから来たか（`sourceId`） |
| `tags` | 現在残っている汚染タグの集合 |
| `argIndex` | 直前に通った引数の位置（`taintedArgs` の判定用） |

### なぜ `source` を状態に含めるのか

`sourceId` を含めない場合、2 つの異なるソースからの汚染が 1 つに融合し、
「どの入力が原因か」を説明できなくなります。
含めることで、検出ごとに「原因となった入力」を特定できます。

代償として状態数がソース数に比例して増えますが、
後述のタグ集合の単調性により、実用上は問題になりません。

### `argIndex` を状態に含める理由

`taintedArgs: [1]` のような指定は「第 2 引数として渡された汚染だけを報告する」
という意味です。汚染がどの引数位置を通ってきたかを追う必要があります。

重要な設計判断: **`argIndex` は推測しません。**
直前の辺が `kind: 'argument'` のときだけ設定し、
関数・コールバックへ入るとリセットします。
推測すると「引数 1 のはずが実は 0」という誤判定が起き、
`taintedArgs` の意味が崩れます。

## 3. ワークリスト法

```text
入力: アノテーション済みグラフ G、ルール集合 R
出力: 検出の集合 F

1. 各ソース出現 s ∈ sources について、初期トークン (s.node, s.id, s.kinds, ⊥) を投入
2. ワークリスト W を初期トークンで初期化
3. while W ≠ ∅:
4.     (node, source, tags, arg) ← W.pop()
5.     もし tags = ∅ なら continue                    # 全部無害化された
6.     もし node ∈ sinks なら considerSink(...)          # 検出の記録
7.     for each 出力辺 e = (node → next) ∈ G:
8.         tags' ← sanitizeAt(next, tags)               # next がサニタイザならタグを落とす
9.         arg'  ← groundArg(e, arg)                    # e が argument 辺ならその位置
10.        もし (next, source, tags', arg') が未訪問なら:
11.            訪問済みに追加
12.            W.push((next, source, tags', arg'))
13. F を決定的な順序へ整列し、重複を除去して返す
```

### 停止性

停止性は **状態空間が有限** であることから従います。

- `node`: 有限（グラフのノード数）
- `source`: 有限（ソース出現数）
- `arg`: 有限（引数の最大数 + 未設定）
- `tags`: 有限（タグの語彙は 9 種類 → 部分集合は 2⁹ = 512）

したがって状態数は `|V| × |S| × 9 × 512` で上界を持ち、
訪問済み集合により各状態は高々 1 度しか処理されません。

### サニタイザの単調性

タグ集合は「減る一方」です。`sanitizeAt` はタグを追加しません。
この単調性により、ループを何度回っても状態が新しく増え続けることがなく、
停止性と不動点の一意性が保証されます。

`valid: false` のサニタイザ（用法が誤っているもの）は
**何も落としません**。これは「サニタイザを呼べば安全」という
誤った推論を避けるためです。

---

## 4. 関数をまたぐ伝播

DFG は関数内の辺しか持ちません。関数をまたぐ流れは
解析時に **補助辺を合成** して扱います。

| 種類 | 合成する辺 | 目的 |
| --- | --- | --- |
| 引数 → 仮引数 | `callNode → callee.param[i]` | 呼び出し先の引数を汚染する |
| 戻り値 | `callee.returnNode → callNode` | 戻り値を汚染する |
| コールバック | `callNode → callback.param[i]` | 高階関数の引数を渡す |

ただし **IR が既に辺を張っている場合は合成しません**（二重辺を避けるため）。
そのため IR 側は「解決できた静的呼び出し」と
「コールバック配線」に対して辺を張り、
解析側は残りを補います。

### 再帰の扱い

再帰・相互再帰では補助辺の合成が循環します。
状態の重複排除（訪問済み集合）により、
同じ状態を 2 度処理しないため自然に収束します。

それでも収束が遅い病的なケースに備え、
**1 関数あたりの反復上限** を設けています。
上限に達した関数は `stats.truncated` と診断に記録され、
「打ち切った」ことが利用者に伝わります。黙って諦めません。

### `maxCallDepth` の意味

再帰的な**再入**の回数だけを制限します。
非再帰の呼び出し連鎖（`a → b → c → d`）は制限しません。

これは意図的な設計です。深い呼び出し連鎖は実務で普通に現れ、
そこで解析を打ち切ると検出漏れになります。
一方、再帰の展開は本質的に停止しないため上限が必要です。

## 5. 根拠（proof）の組み立て

トークンは経路 `path: nodeId[]` を持ちます。
シンクに到達したとき、この経路を `ProofStep[]` へ変換します。

```ts
interface ProofStep {
  readonly nodeId: string;
  readonly file: string;
  readonly range: Range;
  readonly label: string;
  readonly role: 'source' | 'propagate' | 'sanitize' | 'sink';
  readonly note?: string;
}
```

### 経路は最短のものを使う

同じ状態に複数の経路で到達した場合、**先に到達した経路**を保持します。
幅優先（FIFO のワークリスト）なので、これは最短経路になります。

最短経路を選ぶ理由:

1. 人が読むときに短い方が理解しやすい
2. 経路長が状態に含まれないため、状態数が増えない

### 経路の例

```
req.query.id                      ← source
  └─ id                           ← propagate（代入）
      └─ 'SELECT …' + id          ← propagate（連結）
          └─ sql                  ← propagate（代入）
              └─ db.query(sql)    ← sink
```

サニタイザを通った場合はそのステップも記録され、
「どこで無害化されたか（されなかったか）」が分かります。

## 6. 過剰検出との戦い

汚染解析の実用上の難しさは、検出漏れよりも **過剰検出** にあります。
ノイズの多いツールは使われなくなるからです。

本エンジンで採用している対策:

| 対策 | 効果 |
| --- | --- |
| タグを 9 種類に分ける | `escapeHtml` が `sql` を落とさない等、文脈を区別できる |
| タグ単位のサニタイズ | `parseInt` は全タグを落とす（数値は注入を起こせない） |
| 用法の検証 | 「プレースホルダのつもり」を正しく評価できる |
| シンクごとの引数指定 | `report.render(name, html)` の第 2 引数だけを検査できる |
| 除外パス | 生成物・依存を最初から対象外にする |
| 重複の抑制 | 入れ子になった式への二重報告を 1 件に畳む |

### それでも残る過剰検出

ベンチマークで残っている 2 件は、どちらも既知の限界です。

1. **`res.send(ファイル内容)`** — ディスクから読んだ内容が
   呼び出し元の `html` タグを引き継ぐため、警告レベルで報告されます。
   ファイルの内容が HTML として解釈されるかは静的に決められません。
2. **許可リスト検証** — `ALLOWED.has(x) ? x : '/home'` は
   実質的に無害化ですが、三項演算子の「どちらかの枝」として
   データフロー上は `x` が流れています。ガード節の認識は
   制御フロー解析を必要とするため、現時点では未実装です。

これらを「直す」には解析の精度を上げる必要があり、
ヒューリスティックで黙らせると本当の脆弱性を隠します。
したがって **直さず、測って、文書化する** 方針を取っています。

## 7. 決定性

同じ入力から同じ出力が得られることは、CI で差分を見るために必須です。

| 箇所 | 対策 |
| --- | --- |
| ファイル探索 | 辞書順に固定 |
| ノード ID | 構築順の連番（`<関数ID>#<連番>`） |
| 辺の整列 | 比較関数を固定（ロケール非依存の文字列比較） |
| 検出の整列 | ファイル → 行 → 列 → ruleId |
| 重複除去 | 整列後に先勝ちで除去 |
| レポータ | 再ソートしない（正準順序はエンジンが決める） |
| フィンガープリント | 検出 ID（位置から決まる） |

文字列比較に `localeCompare` を使っていないのは意図的です。
ロケール依存の順序は環境によって変わり、CI の差分が
実行環境で揺れる原因になります。

## 8. 計算量

実測（ベンチマーク 31 ファイル / 45 関数）: **約 40ms**。

理論上の上界は `O(|V| × |S| × 2^|T| × |E|)` ですが、
実際には次の理由で遥かに小さくなります。

- タグ集合はソースごとに同じ初期値から始まり、
  サニタイザを通るまで減少しないため、実際に現れる組み合わせは少ない
- 訪問済み集合により各状態は 1 度だけ処理される
- 関数をまたぐ補助辺は必要になったときだけ合成される

大規模なリポジトリでは、ファイル単位の並列化が次の改善点です。
現状は単一プロセス・逐次処理です。

## 9. 実装中に踏んだ不具合

記録として残します。同じ設計を選ぶ人が同じ穴に落ちないように。

| 症状 | 原因 | 対策 |
| --- | --- | --- |
| 仮引数ノードが `global` ノードに覆い隠される | 仮引数の宣言位置を「型注釈を含む範囲」で登録していたため、識別子の位置と一致しなかった | 識別子そのものの範囲で登録する |
| 動的キー `o[k]` に自己辺ができる | 基底と読み出し結果が同じラベルに潰れ、同じノードと誤認された | 動的アクセスを `o[<dynamic>]` として区別する |
| 変数宣言の初期化子が二重に走査される | 宣言の収集と本体の走査の両方で式を作っていた | 初期化子の走査を 1 箇所に集約する |
| モジュール直下のコードが解析されない | 関数文脈が無いコードを黙って捨てていた | `<module>` 疑似関数として扱う |
| 1 つの呼び出しが 2 件報告される | `await axios.get(x)` の call と await の両方にシンクが付いた | 包含関係のある同一ルールの検出は広い方だけ残す |
| 単一ファイル指定で相対パスが空になる | 解析ルートをファイル自身にしていた | ファイル指定時は親ディレクトリを基準にする |

最後の 2 つは「テストでは気づきにくく、実際に走らせて初めて出る」種類の不具合でした。
ベンチマークと実行例を最初から用意していたことが効いています。
