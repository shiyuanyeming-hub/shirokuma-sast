# 面接ガイド

このプロジェクトについて聞かれたときに、何をどう答えるかをまとめています。
「作ったものの説明」ではなく「設計判断の説明」ができるようにするのが目的です。

---

## 30 秒で説明する

> TypeScript のコンパイラ API を使って、AST からデータフローグラフを組み、
> 外部入力が危険な操作へ到達する経路を追跡する SAST エンジンです。
> 正規表現で関数名を探すツールではないので、変数を経由した伝播や
> 関数をまたいだ伝播も追えます。サニタイザを理解しているので、
> エスケープ済みのコードは報告しません。
> 検出には必ずソースからシンクまでの経路が付くので、
> 「本当に到達するのか」を確認する手間が省けます。
> 精度は自作の教師データで測っていて、適合率 91%・再現率 100%・F1 0.955 です。

## 技術的な深掘り

### Q. なぜ AST を歩くだけではだめなのか

変数と関数呼び出しで必ず破綻します。

```ts
const id = req.query.id;
const sql = 'SELECT * FROM users WHERE id = ' + id;
db.query(sql);
```

`req.query` と `db.query` は同じ関数内にありますが、
その間に 2 つの変数を経由しています。
構文木を上から順に眺めるだけでは「`sql` に入っている値が
`req.query.id` 由来かどうか」は分かりません。

そこで一度 **データフローグラフ** に落とします。
ノードが「値の発生点」、辺が「値の移動」です。
すると上記は `req.query.id → id → 'SELECT …' + id → sql → db.query`
という経路になり、到達可能性の問題として解けます。

### Q. サニタイザをどう扱っているか

**タグ集合** で扱っています。汚染には種類（`sql` / `html` / `command` など 9 種）があり、
サニタイザは **自分の担当するタグだけ** を落とします。

```ts
const safe = escapeHtml(req.query.comment);  // html タグが落ちる
db.query('… = ' + safe);                      // sql タグは残る → 正しく検出
```

ここを「サニタイザを通ったら全部安全」にしてしまうと、
HTML エスケープした値を SQL に連結しているコードを見逃します。

さらに **用法まで検証** しています。
`db.query` はプレースホルダとして使われているときだけサニタイザです。

```ts
db.query('… = $1', [id]);   // 有効（サニタイザ）
db.query(sqlVar);           // 無効（ただのラッパー。汚染は残る）
```

判定は「第 1 引数が文字列リテラル、または補間を含まないテンプレートリテラル」です。
`static-sql` という検証種別として実装しています。

### Q. アルゴリズムは何か

ワークリスト法です。状態は `(ノード, ソース, タグ集合, 引数位置)` の 4 つ組で、
訪問済み集合で重複を排除しながら不動点まで回します。

停止性は状態空間が有限であることから従います。
タグ集合は 9 種の部分集合なので 2⁹ = 512 通り、
ノードとソースも有限です。
さらに **タグは減る一方**（サニタイザは追加しない）なので、
同じ状態を何度も処理することがありません。

再帰・相互再帰は状態の重複排除で自然に収束しますが、
病的なケースに備えて 1 関数あたりの反復上限を設け、
打ち切った場合は `stats.truncated` に記録します。
**黙って諦めない** ことを重視しています。

### Q. 関数をまたぐ伝播はどう実現しているか

DFG は関数内の辺しか持ちません。関数をまたぐ部分は解析時に補助辺を合成します。

| 種類 | 合成する辺 |
| --- | --- |
| 引数 → 仮引数 | `callNode → callee.param[i]` |
| 戻り値 | `callee.returnNode → callNode` |
| コールバック | `callNode → callback.param[i]` |

コールバックの配線は IR 構築側が担当します。
`arr.map(x => sink(x))` の「第 0 引数」と「コールバックの第 0 仮引数」の対応は
データフローの辺では表現できない（関数値は「値」ではない）ため、
`SolverHints.callbackLinks` として別に渡しています。

型を分けたのは、IR を「整形式のグラフ」に保ちつつ、
グラフでは表現できない意味づけを伝えるためです。
IR 構築はルールを知らず、解析エンジンは構文を知りません。

### Q. 検出の「根拠」はどう作っているか

トークンが経路（ノード ID の列）を持ち、シンク到達時に `ProofStep[]` へ変換します。
ワークリストが FIFO なので、複数の経路がある場合は最短経路が残ります。

これを SARIF の `codeFlows` に入れているので、
GitHub の Code Scanning 上でそのまま経路が表示されます。

### Q. なぜ IR 構築とルール適用を分けたのか

ルールを 1 つ足すたびにパーサを触る状況を避けるためです。

- **IR 構築** は「値がどこからどこへ流れるか」だけを決めます。ルールを参照しません。
- **ルール適用** は「どのノードがソース／サニタイザ／シンクか」だけを決めます。構文木を走査しません。

この分離のおかげで、IR のテストはルール無しで書け、
ルールのテストは構文に依存しません。
`test/ir/`、`test/analysis/`、`test/reporters/` がそれぞれ独立して動いています。

### Q. 精度はどう測ったか

`benchmarks/` に教師データを置き、`npm run bench` で測定しています。
脆弱 21 箇所と安全 13 箇所のラベル付きで、行番号まで一致させて照合します。

現在: **適合率 91.3% / 再現率 100.0% / F1 0.955**（TP 21 / FP 2 / FN 0）。

重要なのは、**安全とラベルした箇所への検出も偽陽性として数えている** ことです。
これによりサニタイザを理解できているかが指標に現れます。

残っている 2 件の偽陽性は README に明記しています。
数値を良く見せるために教師データを緩めることはしていません
（実際、`res.json` を XSS シンクと誤ってラベルしていた箇所は
「エンジンではなく教師データが間違っていた」と判断して修正しました）。

### Q. 苦労した点は

**過剰検出との戦い**です。検出漏れより、ノイズの方が実用上の害が大きい。
使われなくなるツールに価値はありません。

具体的には、タグを 9 種に分ける、サニタイザの用法まで検証する、
シンクごとに検査する引数を指定できるようにする、といった対策を入れました。

もう 1 つは **テストでは気づけない不具合** です。

- 1 つの呼び出しが 2 件報告される（`await axios.get(x)` の call と await の両方にシンクが付く）
- 単一ファイルを指定すると相対パスが空になる（解析ルートをファイル自身にしていた）

3 つ目は **ドッグフーディング**（自作ツールで自分自身を解析する）で見つけました。
`this` 式と正規表現リテラルが `unknown` ノードに落ちており、
87 件の診断が出ていました。`this.db.query(...)` のようなコードで
レシーバを追えなくなる問題です。自分のコードを解析させると、
テストでは踏まない入力が一気に増えるので効きます。

どれも単体テストは緑のまま、実際に走らせて初めて出ました。
ベンチマーク・実行例・セルフスキャンを最初から用意していたことが効いています。

### Q. 制限は何か

率直に答えます。

- **型情報を使っていない。** 単一ファイルの AST だけを読むので、
  npm パッケージをまたぐ伝播は追えません。
- **フロー感度が限定的。** 分岐の到達可能性を判定しないので、
  `if (isAdmin) { … }` の中も報告します。
- **ガード節を理解しない。** `ALLOWED.has(x) ? x : '/home'` のような
  許可リスト検証を無害化として認識しません（偽陽性 2 件のうち 1 件がこれです）。
- **健全性は保証しない。** 見逃しは必ず存在します。

「これで全部見つかります」とは言いません。
測った範囲の数値と、残っている誤りをセットで提示するのが誠実だと考えています。

## 想定質問と回答案

### 「既存の SAST（CodeQL、Semgrep、Snyk）と何が違うのか」

競合として答えません。用途が違います。

- CodeQL は型解決と制御フローを含む本格的な解析で、精度も上です。ただし
  セットアップが重く、クエリ言語の学習コストがあります。
- Semgrep はパターンマッチが高速で、独自ルールを書きやすい。
  ただしクロスファンクションのテイント解析は限定的です。

本プロジェクトは「TypeScript の型システムを **使わずに**、
単一ファイルの AST だけでどこまでできるか」を突き詰めたものです。
CI に 1 分で組み込めて、依存も 1 つ（TypeScript 本体）だけで動きます。
その代わり精度は既存ツールに劣ります。トレードオフを理解して使うべき道具です。

### 「なぜ TypeScript で書いたのか」

3 つ理由があります。

1. 解析対象と同じ言語なので、AST の扱いに齟齬が出ない。
   TypeScript コンパイラ API は TypeScript から使うのが最も自然です。
2. 型定義が公開 API の仕様になる。`src/types.ts` がそのまま
   モジュール間のコントラクトとして機能しています。
3. 配布が簡単。`npm install` だけで動き、ネイティブビルドが不要です。

### 「なぜテストが 484 件もあるのか」

層ごとに独立してテストできる設計にした結果です。
内訳は IR 構築 53 件、解析エンジン 73 件、レポータ 65 件、
ルール 120 件、統合 23 件、CLI 30 件、ユーティリティ 23 件などです。

テストは「実装の写経」ではなく、**仕様の固定** として書いています。
たとえば IR には 16 種類の伝播があり、それぞれに 1 つ以上のテストがあります。
仕様を変えたければテストを変える必要があり、その差分がレビューの対象になります。

### 「セキュリティツールなのに、自分のコードの脆弱性は大丈夫なのか」

ドッグフーディングしています。CI の `sarif` ジョブが
自分自身をスキャンして SARIF を GitHub Code Scanning へ上げます。

ただし `--fail-on none` で走らせています。
「自分のコードに指摘が 1 件も無い」ことを主張するのではなく、
**解析が完走し続けること** を継続的に確認するのが目的です。
自作ツールの指摘を消すためにルールを緩めるのは本末転倒なので、
そうならないよう CI では失敗させていません。

### 「次にやるなら何か」

優先順位をつけて答えます。

1. **制御フロー感度** — ガード節（許可リスト検証）を認識できれば、
   現在の偽陽性が減り、実用性が上がります。
2. **型情報の利用** — TypeScript の型チェッカを併用し、
   `string` と `number` を区別できれば、`parseInt` に頼らない
   数値の判定ができます。
3. **ファイル単位の並列化** — 現在は逐次処理です。
   大規模リポジトリでは並列化が効きます。
4. **インクリメンタル解析** — 変更ファイルだけ再解析し、
   サマリをキャッシュする。CI の実行時間に直結します。

## コードを読む順番（面接官向け）

時間が限られている場合、この順で読むと設計意図が伝わります。

| 順 | ファイル | 見どころ |
| --- | --- | --- |
| 1 | `src/types.ts` | モジュール間コントラクト。ここが設計の中心 |
| 2 | `src/ir/contract.ts` | 16 の伝播規則の宣言。IR が何を保証するか |
| 3 | `src/ir/builder.ts` | 2 段階の宣言収集と本体走査。前方参照の解決 |
| 4 | `src/analysis/solver.ts` | ワークリスト法。タグ集合の単調性と停止性 |
| 5 | `src/rules/annotate.ts` | ルールとグラフの突き合わせ。最長一致 |
| 6 | `src/reporters/sarif.ts` | SARIF 2.1.0 への写像と `codeFlows` |
| 7 | `docs/TAINT_ANALYSIS.ja.md` | アルゴリズムの全体像と妥協点 |
| 8 | `benchmarks/manifest.json` | 精度をどう測っているか |

`src/cli/args.ts` は依存を増やさずに引数解析を自前実装した例として、
`src/discovery.ts` は決定的な順序でのファイル探索の例として読めます。
